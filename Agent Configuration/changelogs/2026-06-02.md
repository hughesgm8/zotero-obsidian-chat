## [15:30] FIX: zotero-mcp upgrade and Obsidian plugin startup hang

### Background
Upgrading `fastmcp` to 3.x broke `zotero-mcp` (the MCP server the plugin depends on). Fixing that then exposed a plugin startup hang caused by a changed server behaviour in fastmcp 2.x.

---

## [1] Upgrade zotero-mcp and fix dependency chain

- **Packages changed**: `zotero-mcp` 0.1.2 → `zotero-mcp-server` 0.4.1; `fastmcp` 3.3.1 → 2.14.0; `pyzotero` 1.7.6 → 1.13.0
- **Change**: Uninstalled the obsolete `zotero-mcp` PyPI package and installed `zotero-mcp-server[semantic]`. Downgraded `fastmcp` from 3.x (which removed `Context` from its public API) to 2.14.0 (the version zotero-mcp 0.4.1 was written for). Upgraded `pyzotero` to 1.13.0 which added the `client=` kwarg that zotero-mcp 0.4.1 requires.
- **Reason**: `fastmcp` 3.x is a breaking major version. `from fastmcp import Context` no longer works, crashing the server on startup. The package was also corrupted by a `fastmcp-slim` namespace conflict left over from the 3.x install, requiring a clean removal and reinstall.

---

## [2] Fix: plugin onload blocked by slow server startup

- **File Modified**: `src/main.ts`
- **Change**: Removed `await` from the `startMCPServer()` call inside `onload()`.
- **Logic Update**:
  ```
  # Before
  async onload():
      ...
      await this.startMCPServer()   # blocks Obsidian's plugin loader

  # After
  async onload():
      ...
      this.startMCPServer()         # fire-and-forget; server connects in background
  ```
- **Reason**: zotero-mcp 0.4.1 initialises ChromaDB on startup, which takes longer than Obsidian's plugin-load timeout (~10s). Obsidian showed "plugin taking long to load" and the UI hung until the 60s `waitForReady` timeout fired.

---

## [3] Fix: readiness probe hanging on fastmcp 2.14.0

- **File Modified**: `src/mcp-server.ts`
- **Change**: Replaced both `requestUrl`-based readiness probes (in `tryReuseExistingServer` and `waitForReady`) with a Node `http` probe (`probeServer()`) that has an explicit 3-second per-request timeout.
- **Logic Update**:
  ```
  # New helper
  probeServer() -> Promise<statusCode>:
      http.request(127.0.0.1:port /mcp, GET, Accept: application/json)
      timeout 3s → resolve(0)
      on error → resolve(0)
      on response → resolve(statusCode)

  # Used in both tryReuseExistingServer() and waitForReady()
  const status = await this.probeServer()
  if (status > 0) → server is up
  ```
- **Reason**: In fastmcp 2.14.0, a `GET /mcp` request that includes `text/event-stream` in the Accept header opens a persistent SSE stream. Obsidian's `requestUrl` hangs indefinitely on keep-alive streams, causing `waitForReady` to never progress. Switching to Node `http` with an explicit timeout makes the probe reliable. The Accept header was also changed to `application/json` only, so the server returns a fast `406 Not Acceptable` instead of opening a stream.
